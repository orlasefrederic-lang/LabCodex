**R1. P2: ошибка чтения правил выдаётся за пустой список; удаление может ложно сообщить успех**

Места: `firewall.py:294–310` (`_LIST_BODY`, особенно строка 296), `firewall.py:344–351` (`_REMOVE_BODY`, особенно строки 347–348), `firewall.py:234–238` (`verify_removed`), `firewall.py:569–601` (`FirewallManager._run`). Сходная обработка чтения есть в `_ADD_BODY` и `_ENABLE_BODY`.

Проверка `state_known` срабатывает, когда `backend.state()` выбрасывает исключение. Но реальный PowerShell-скрипт выполняет `Get-NetFirewallRule` с `-ErrorAction SilentlyContinue`. Нетерминирующая ошибка чтения подавляется и становится пустым результатом. Если чтение профилей при этом успешно, `state()` возвращает «правил нет», а не ошибку. Такой результат менеджер считает достоверным.

Подтверждено через настоящий PowerShell с модифицированными штатными тестовыми командлетами:

1. Создать два правила и прочитать их менеджером.
2. Настроить `Get-NetFirewallRule` на `Write-Error -Category PermissionDenied`, оставив `Get-NetFirewallProfile` рабочим.
3. Попросить удалить ранее выбранные правила.
4. Предварительное чтение по имени возвращает пусто; `_REMOVE_BODY` пропускает удаление.
5. Финальное чтение группы тоже возвращает пусто; `verify_removed()` считает результат успешным.

Фактический результат:

```text
actual_rules_remaining = 2
manager.state_known = True
len(manager.entries) = 0
manager.error = ''
message = ('info', 'Убрано из списка: demo.exe')
```

Уточнение: не утверждается, что любой отказ в доступе к Windows Firewall оставляет чтение профилей доступным. Воспроизведён конкретный путь обработки ошибки чтения правил; возможны также другие частичные ошибки чтения. Штатный тест `test_unreadable_state_is_unknown_not_blocked` подменяет `state()` целиком исключением, поэтому проблему внутри PowerShell он не видит.

Исправление: не подавлять все ошибки чтения. Отсутствие конкретного правила/группы обрабатывать отдельно от PermissionDenied и прочих ошибок поставщика. При ошибке чтения сохранять состояние как неизвестное и не подтверждать удаление по пустому результату. Применить этот подход к чтению списка и к поиску правила перед изменением/удалением.

Проверка после исправления: тот же сценарий приводит к сообщению об ошибке и `state_known == False`; не появляется «Убрано из списка». Обычное отсутствие правил при первом запуске продолжает обрабатываться корректно.

**R2. P2: «Снова запрещено» может означать только входящий запрет — исходящее правило отсутствует**

Места: `firewall.py:241–246` (`verify_enabled`), `firewall.py:354–360` (`_ENABLE_BODY`), `firewall.py:546–552` (`FirewallManager.set_enabled`).

Причина: `verify_enabled()` проверяет состояние только тех переданных ID, которые найдены в фактическом списке. Отсутствующие ID исключаются из проверки. Сам скрипт включения тоже пропускает отсутствующие правила. Таким образом успешность включения подтверждается даже без части нужных правил.

Воспроизведение:

1. Создать правила для обоих направлений и временно выключить их.
2. Пока в интерфейсе остаётся старая выбранная запись, удалить исходящее правило внешним способом, например через `wf.msc`.
3. Нажать «Снова запретить».

Результат на модели брандмауэра:

```text
actual_rules = [('in', True)]
message = ('info', 'Снова запрещено: demo.exe')
status = ('blocked', 'запрещена (вх.)')
```

Таблица после перечитывания показывает входящее направление правильно. Ошибка именно в подтверждении полного успеха операции по прежней записи: исходящий запрет не восстановлен. Если исчезли оба правила, сообщение об успехе также возможно при полном отсутствии блокировки.

Исправление: при включении требовать наличие всех выбранных ID и нужное состояние каждого правила. При отсутствии хотя бы одного — сообщать о неполном результате и необходимости заново создать запрет либо явно восстанавливать недостающее правило из проверенного плана. Для выключения отсутствие правила можно считать достигнутым результатом, если это осознанная семантика.

Проверка после исправления: удаление одного/обоих правил между загрузкой списка и повторным включением не приводит к сообщению «Снова запрещено» без полноценного запрета.

**R3. P2: допуск в две секунды всё ещё позволяет приписать старый трафик новому exe**

Места: `model.py:557–570` (`_same_instance`), `model.py:590–606` (`fill_details`).

Причина: сведения с временем создания вплоть до `first_seen + 2.0` принимаются за тот же экземпляр. При наличии `started` сравнение имён/путей вообще не выполняется. Между снимком процессов и запросом подробностей PID может сменить владельца быстрее чем за две секунды; отсутствие уже обработанного события stop не делает эти экземпляры одинаковыми.

Минимальное воспроизведение:

```python
from model import Model

m = Model()
m.resolve_names = False
m.sync_processes({100: ('old.exe', 1)}, now=100.0)
uid = m.by_pid[100].uid
m.on_traffic(100, 'TCP', True, 10,
             '1.1.1.1', 443, '10.0.0.1', 50000, 100.1)
m.process_pending()
# Подробности уже принадлежат новому владельцу PID.
m.fill_details(uid, {'path': r'C:\new.exe', 'started': 100.5}, now=100.6)
print([(p.name, p.started, p.sent) for p in m.procs.values()])
# Фактически: [('new.exe', 100.5, 10)]
```

Ожидается отдельная запись new.exe без старых 10 байт, сохранение имени и трафика old.exe. Неверный путь в истории может также повлиять на последующий ручной выбор программы для блокировки. Сценарий не означает автоматической блокировки неправильного exe самим монитором.

Штатный тест смены PID между снимком и подробностями использует разрыв от 100 до 150 секунд; он не проверяет границу двухсекундного допуска.

Исправление: проверять несовместимость известных имён/путей независимо от наличия времени создания. Не считать процесс, созданный позже момента достоверного наблюдения старого PID, тем же экземпляром только из-за широкого допуска. Для надёжной идентификации хранить точное время создания процесса и отдельно учитывать погрешность времени доставки ETW/снимка; одно лишь уменьшение константы не закрывает все случаи.

Проверка после исправления: повторение приведённого сценария с разрывами 0.1, 0.5 и 1.9 секунды не переносит старые байты новому exe.

**R4. P2 при запоздавшей доставке событий: накопитель объединяет трафик разных экземпляров PID раньше, чем определяется владелец**

Места: `model.py:187–199` (`on_traffic`), `model.py:381–384` (`_apply_traffic`).

Исправление выбора экземпляра по времени события работает для отдельного события. Но ключ накопителя — только `(pid, proto, daddr, dport, saddr, sport)`. Если после нового start приходит старый запоздавший пакет, а затем новый пакет с тем же набором адресов и портов, они объединяются. При разборе вся сумма передаётся экземпляру, определённому по времени первого пакета `t0`.

Минимальное воспроизведение:

```python
from model import Model

m = Model()
m.resolve_names = False
m.on_process_start(100, 1.0, r'C:\old.exe')
m.on_process_stop(100, 3.0)
m.on_process_start(100, 10.0, r'C:\new.exe')
for ts, size in [(2.5, 7), (11.0, 9)]:
    m.on_traffic(100, 'TCP', True, size,
                 '1.1.1.1', 443, '10.0.0.1', 50000, ts)
m.process_pending()
print({p.name: p.sent for p in m.procs.values()})
# Фактически: {'old.exe': 16, 'new.exe': 0}
# Ожидается: {'old.exe': 7, 'new.exe': 9}
```

Штатный тест `test_late_packet_goes_to_previous_instance` использует разные адреса и локальные порты для двух экземпляров; поэтому записи накопителя не объединяются и тест проходит.

Исправление: не объединять события разных времён жизни процесса до определения владельца; сохранить необходимую информацию о времени/границах экземпляров. После выбора экземпляра агрегировать по его UID. Учитывать цену решения при большом потоке событий, не возвращая тяжёлую обработку на каждый ETW callback без необходимости.

Проверка после исправления: один и тот же поток адресов/портов при запоздавших событиях сохраняет 7 и 9 байт у соответствующих экземпляров; проверить оба порядка доставки. Порядок событий здесь задан синтетически, его реальная частота в Windows не измерялась. Это конкретный недостаток заявленной поддержки запоздавшей доставки, а не доказательство постоянной ошибки счётчиков.

**Как повторить дополнительные проверки**

Скачать [NETMON_REVIEW_V1_1_CHECKS.py](NETMON_REVIEW_V1_1_CHECKS.py) и указать каталог с распакованными `model.py`, `firewall.py` и `tests`:

```text
python NETMON_REVIEW_V1_1_CHECKS.py "путь/к/netmon" --pwsh "путь/к/pwsh"
```

Без `--pwsh` скрипт ищет PowerShell в `NETMON_PWSH` или PATH; если не найдёт, пропустит только R1. Он использует тестовые функции и временное JSON-хранилище, не изменяет системный брандмауэр. Поле `defect_reproduced: true` означает воспроизведённый дефект, а не успешность исправления. После исправления соответствующие assertions этого диагностического скрипта должны перестать выполняться; для постоянного набора тестов нужно проверять правильное ожидаемое поведение.

Результат текущего запуска: все четыре сценария воспроизведены. Сначала рекомендуется закрыть R1 и R2, затем R3 и R4 и выполнить интеграционную проверку TCP/UDP, IPv4/IPv6 и правил файрволла на Windows. Успешный штатный набор из 80 тестов сам по себе не заменяет эту проверку.
