## V14-1 — P2, новая регрессия: чужой запоздавший start создаёт дубликат текущего процесса

**Места:** model.py:404–418, 420–449, 450–459.

Сначала текущий процесс найден снимком, затем его полный путь и время создания подтверждены через fill_details. Позднее приходит start прежнего владельца PID. Если времена близки, _late_start принимает старое событие за запуск текущего процесса: сравнивает время, но не проверяет image/path.

После этого текущая запись получает etw_started=True. Когда приходит её настоящий start, новая логика считает, что «свой запуск уже был», завершает текущую запись и создаёт вторую.

### Воспроизведение

Все события относятся к PID 100; времена — условные секунды.

1. Снимок в 10.02 находит app.exe.
2. fill_details сообщает **C:\New\app.exe**, created=10.01.
3. Приходит его пакет в 10.025, 10 байт.
4. С опозданием приходит start **C:\Old\app.exe**, timestamp=10.0.
5. Затем настоящий start **C:\New\app.exe**, timestamp=10.015.
6. Его следующий пакет в 10.03, 9 байт.

**Ожидается:** один экземпляр New/app.exe с created=10.01, ended=None, sent=19.

**Фактически в 1.4:**

~~~text
C:\New\app.exe: started=10.01,  ended=10.015, sent=10
C:\New\app.exe: started=10.015, ended=None,   sent=9
~~~

У первой записи время завершения оказывается раньше first_seen=10.02 и уже учтённого пакета в 10.025. Общая сумма байтов здесь сохраняется, но экземпляры, времена и распределение трафика по ним неверны. При группировке по программе дубликат может быть менее заметен.

**В 1.3 тот же тест проходит:** остаётся один экземпляр. Поэтому это именно регрессия 1.4, а не повтор предыдущего замечания.

**Рекомендация:** до установки etw_started согласовывать событие с известным полным путём и временем создания экземпляра. Конфликтующий start более старого владельца не должен подтверждать запуск текущего. Недостаточно просто вернуть False из _late_start при несовпадении пути: последующая ветка _apply_start тоже должна правильно обработать старое событие, не завершая текущий процесс.

Тест: test_v14_1_late_other_exe_start_does_not_duplicate_current.

## V14-2 — P2, унаследовано: после перезапуска монитора сливается история разных exe

**Места:** model.py:758–761 и _reattach, строки 819–865.

Проверка восстановления истории принимает совпадающее имя файла и разницу времён создания меньше двух секунд. Полные пути не сравниваются. За время, когда монитор закрыт, PID может перейти другой программе с тем же basename.

### Воспроизведение

1. Сохранена работающая **C:\Old\app.exe**, PID 100, created=100.0, sent=10.
2. Монитор закрыт; Old завершается.
3. PID 100 получает **C:\Other\app.exe**, created=100.4.
4. Монитор запускается снова. Снимок и fill_details сообщают новый путь и время создания.
5. Новая программа отправляет 20 байт.

**Ожидается в истории:**

~~~text
C:\Old\app.exe:   started=100.0, sent=10
C:\Other\app.exe: started=100.4, sent=20
~~~

**Фактически — и в памяти, и после сохранения в SQLite:**

~~~text
C:\Other\app.exe: started=100.0, sent=30
~~~

Временная запись нового процесса сливается со старой; путь старой истории переписывается. Это тот же класс ошибки идентификации, который раньше исправлялся в fill_details, но здесь используется отдельная проверка восстановления истории.

**Воспроизводится в 1.3 и 1.4. Не появилось из-за последнего исправления.**

**Рекомендация:** применять при восстановлении истории проверку идентичности процесса, учитывающую нормализованный полный путь и достоверное время создания. Совпадающего basename и двухсекундного допуска недостаточно. Также нужен тест повторного запуска того же exe с новым временем создания.

Тест: test_v14_2_history_does_not_merge_other_full_path.

## V14-3 — P2, унаследовано: запись из снимка поглощает следующий быстрый запуск

**Места:** model.py:383–392, 394–418, 420–449.

seen_by_etw устанавливается, только когда запись создаётся внутри _proc_at. Если запись уже пришла из снимка, последующие реальные пакеты не сохраняют точный момент наблюдения ETW для решения о следующем start. При этом _started_instance не проверяет конфликт полного пути.

### Воспроизведение

1. Снимок old.exe в 100.0; fill_details сообщает C:\old.exe, created=99.6.
2. Его пакет в 100.0: 10 байт.
3. Start C:\new.exe в 100.02.
4. Пакет нового процесса в 100.03: 9 байт.
5. С опозданием приходит stop прежнего процесса с timestamp=100.01.

**Ожидается:** old.exe с 10 байтами и завершением 100.01; new.exe с 9 байтами, работающий.

**Фактически:** одна завершённая old.exe с 19 байтами.

Здесь stop старого процесса доставлен после нового start. Это отличается от уже исправленного V13-1 с явным stop перед start. Допуск снимка 0,05 с и START_LAG позволяют ошибочно принять второй start за первый, хотя есть конфликт пути и более ранний пакет.

**Воспроизводится и в 1.3.**

**Рекомендация:** сохранять достоверное время наблюдения ETW и для уже существующих записей; учитывать его при сопоставлении start. Просто выставить seen_by_etw=True, оставив first_seen от снимка, недостаточно: происхождение и фактическое время наблюдения должны оставаться согласованными. Конфликт известных путей — отдельное основание не объединять записи.

Тест: test_v14_3_snapshot_with_traffic_does_not_absorb_next_start.

## V14-4 — P2, унаследовано: поздний старый start присваивается новому процессу с неизвестным временем запуска

**Места:** model.py:420–424, 404–418; последствие — _clamp_previous, строки 367–375.

При поиске экземпляра для позднего start рассматривается последняя запись. Если её started ещё неизвестно, _late_start может принять событие, которое произошло раньше уже известного завершения предыдущего владельца PID. Нижняя граница, вытекающая из соседнего экземпляра, здесь не проверяется.

### Воспроизведение

1. Пакет старого PID 100 в 1.0, 10 байт; start пока не получен.
2. Его stop в 3.0.
3. Пакет нового владельца PID в 4.0, 9 байт. Создаётся второй экземпляр с неизвестным started.
4. Приходит запоздавший start C:\old.exe с timestamp=0.9.

**Ожидается:** заполнить путь и started=0.9 первого экземпляра, сохранить его ended=3.0; второй оставить отдельным с 9 байтами.

**Фактически:** имя old.exe и started=0.9 получает второй экземпляр. _clamp_previous затем меняет ended первого с 3.0 на 0.9 — раньше его собственного пакета в 1.0.

**Воспроизводится и в 1.3.** Новый штатный тест late_start_of_older_instance проверяет случай, когда start нового экземпляра уже известен; вариант с неизвестным started остаётся непокрытым.

**Рекомендация:** при сопоставлении позднего start учитывать границы жизни соседних экземпляров. Старое событие до известного stop должно дополнять старую запись, а не более новую с неизвестным started. Перед изменением соседних границ проверять согласованность с уже известными событиями.

Тест: test_v14_4_late_start_belongs_before_known_stop.

## Материалы для исправления

[NETMON_REVIEW_V1_4_CHECKS.py](NETMON_REVIEW_V1_4_CHECKS.py) — четыре самостоятельных unittest-метода. Они используют публичные методы модели и временную SQLite-базу; не меняют Windows Firewall и не отправляют сетевые запросы.

~~~bat
python NETMON_REVIEW_V1_4_CHECKS.py "C:\путь\к\распакованному\netmon"
python NETMON_REVIEW_V1_3_CHECKS.py "C:\путь\к\распакованному\netmon"
~~~

Штатный набор запускается из каталога netmon:

~~~bat
python -m unittest discover -s tests -v
~~~

Для восьми PowerShell-проверок нужен pwsh в PATH либо переменная NETMON_PWSH с путём к нему. В этой проверке все восемь реально выполнены; пропусков не было.

После исправления важно сохранить прохождение прежних сценариев: явный stop → быстрый start, одинаковый exe при повторном запуске, запоздалый start своего экземпляра и отложенные пакеты соседних экземпляров.
