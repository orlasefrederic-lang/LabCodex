# NetStrazh 3.5: неверное исключение прокси при холодном запуске с lockdown

Проверка 15 ноября 2026. Исходники неизменённого архива `Netstrazh 3.5.zip`, коммит `dd365f008db6563365a72d5aa5448f72af001dd6`. Пути приложения ниже относительны корню `Lab-claude-confident-cray-n5kkx8/NetStrazh/app/src/main/java/lab/netstrazh/` внутри архива.

## Подтверждённое поведение

**Средний приоритет: доступность связки с прокси при запуске на Android 10. Утечка данных этим результатом не установлена.**

Если Android уже настроен на «Постоянная VPN» и «Блокировать соединения без VPN», а в настройках прокси сохранены `appPkg=com.v2ray.ang` и `bypassApp=true`, новый экземпляр VPN-службы 3.5 может установить интерфейс с v2rayNG в списке исключений. Это противоречит намерению новой логики приложения: при lockdown прокси должен оставаться внутри VPN, иначе системная блокировка лишает исключённый UID обычного доступа к сети.

Это отдельный дефект холодного запуска. Для него **не требуется** вручную помечать v2rayNG «мимо Стража» в правилах приложений. Описанное в `lifecycle-audit.md` ручное исключение — другой, дополнительный конфликт настроек.

В двух запусках `LockdownRealV2rayTest` подготовка не достигла требуемой готовности. Каждый запуск завершился как **0 выполненных сценариев и 1 ошибка BeforeClass**, а не как три проваленных сетевых сценария:

- [Первоначальный лог](logs/LockdownRealV2rayTest.log): общая длительность с подготовкой/завершением 75,605 с; отдельные условия готовности ещё не записывались.
- [Повтор с диагностикой](logs/LockdownRealV2rayTest-diagnostic-repeat.log): общая длительность 74,415 с. Условия проверки не ослаблялись. После 60-секундного ожидания зафиксировано:

```text
running=true
cfgMatches=true
prefsMatch=true
systemLockdown=true
reportedLockdown=false
appliedExcluded=[com.v2ray.ang]
engineStartedAt=1794722769664
captureVerifiedAt=1794722770834
captureBroken=false
captureRecoveries=0
proxyUid=-3
installedUid=10118

```

Следовательно, система уже считала VPN работающим в lockdown, собственный пробный пакет приложения прошёл через текущий интерфейс, однако приложение сохранило ложное значение lockdown и действительно исключило прокси. `-3` здесь — `Upstream.UID_NONE`, а не UID установленной v2rayNG. Сам по себе этот маркер не доказывает отсутствие службы: [дополнительная диагностика](logs/lockdown-readiness-diagnostic.txt) показывает активный `CoreProxyOnlyService` в процессе `com.v2ray.ang:daemon`. Служба была в режиме прокси, не второго VPN.

Эти два запуска устанавливают неправильную конфигурацию реального интерфейса и срыв подготовки. Они **не отправляли тестовые TCP/UDP payload после подготовки**, поэтому их результат отдельно не следует описывать как доказанную передачу данных в обход или как измеренную длительность отсутствия интернета.

## Причина в коде и контракте Android 10

1. `vpn/FirewallService.kt:234` вызывает `excludedNow()` **до** `Builder.establish()` на строке239. Полученный список передаётся `addDisallowedApplication` на строке236.
2. `excludedNow()` на строках304–306 читает `isLockdownEnabled`, сохраняет его в `FirewallService.lockdown` и добавляет прокси к исключениям, если ответ false.
3. На Android 10 этот API означает состояние **текущего установленного VPN вызывающего приложения**, а не просто сохранённый системный переключатель. До первого `establish()` отсутствие действующего интерфейса даёт false даже при заранее включённой системной блокировке.
4. После запуска первая успешная самопроверка обновляет время захвата, но строка198 выполняет перепроверку исключений только при `!first`. Поэтому первая успешная проверка пропускает исправление. Следующая плановая проверка назначается через `CAPTURE_EVERY_MS=60000` (строки195,422).

Публичный исходный код AOSP Android 10 подтверждает последовательность:

- [`VpnService.isLockdownEnabled()`](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-10.0.0_r47/core/java/android/net/VpnService.java#L401) вызывает `isCallerCurrentAlwaysOnVpnLockdownApp()`.
- [`ConnectivityService.isCallerCurrentAlwaysOnVpnLockdownApp()`](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-10.0.0_r47/services/core/java/com/android/server/ConnectivityService.java#L7139) возвращает true только при ненулевом `getVpnIfOwner()` и включённом lockdown.
- [`getVpnIfOwner()`](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-10.0.0_r47/services/core/java/com/android/server/ConnectivityService.java#L7076) получает `vpn.getVpnInfo()`; при null возвращает null.
- [`Vpn.getVpnInfo()`](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-10.0.0_r47/services/core/java/com/android/server/connectivity/Vpn.java#L1567) возвращает null до `isRunningLocked()`. [Проверка работающего VPN](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-10.0.0_r47/services/core/java/com/android/server/connectivity/Vpn.java#L1148) требует существующих network agent и интерфейса.

Сохранённые выдержки с URL и номерами строк: [VpnService](resource-audit/aosp29-VpnService.java.txt), [ConnectivityService](resource-audit/aosp29-ConnectivityService.java.txt), [Vpn](resource-audit/aosp29-Vpn.java.txt). Это проверка опубликованного исходного кода AOSP Android 10; она не выдаётся за анализ точного бинарного build эмулятора или всех реализаций производителей.

## Восстановление и исправление

Нельзя утверждать, что ошибка сохраняется навсегда. В коде есть последующая плановая перепроверка примерно через минуту, обработка новых start-команд и `FirewallService.recheck()` при возврате в UI. Эти пути могут пересоздать VPN с правильным списком. Рассмотренные два теста прекратили ожидание через 60 с и затем остановили службу, поэтому не устанавливают время автоматического восстановления позже этого предела.

Рекомендуется не трактовать ответ API до первого `establish()` как достоверное выключение системного lockdown. Возможный подход: изначально оставлять автоматически исключаемое прокси-приложение внутри VPN, затем сразу после установки интерфейса читать актуальное состояние и применять нужный список. Как минимум, перепроверка нужна после первого установления/первого подтверждённого захвата, без условия `!first`. При реализации следует отдельно проверить число пересозданий, стабильность обновления уведомления и соблюдение ручных правил пользователя.

Временный вариант настройки — не запрашивать автоматическое исключение прокси (`bypassApp=false`) при использовании системной блокировки. Он устраняет именно зависимость от раннего чтения состояния. Системную блокировку ради обхода этой ошибки отключать не требуется. Работу восстановления через уже существующий `recheck()` проверяет отдельный сценарий ниже.

## Отдельная проверка payload и существующего recheck

Выполнен [LockdownColdStartReviewTest](test-src/lab/netstrazh/LockdownColdStartReviewTest.kt): **1/1 диагностический сценарий завершился успешно**. Он не меняет код приложения или системные переключатели:

1. Запускает свежую VPN-службу с автоматическим исключением прокси при уже включённом системном lockdown.
2. Ждёт подтверждения захвата текущего интерфейса и фиксирует противоречивое состояние системы/приложения и неправильное исключение.
3. Отправляет ограниченный по времени HTTP-запрос с уникальной меткой через реальную v2rayNG на контролируемый локальный ответчик.
4. Вызывает существующий `FirewallService.recheck()` на главном потоке — тот же механизм, который UI вызывает при возобновлении.
5. Требует нового проверенного интерфейса без исключения прокси, правильного UID, точных TCP/UDP-ответов и учёта обоих UID.

**Успех этого диагностического сценария означает воспроизведение дефекта и восстановление существующим recheck, а не отсутствие дефекта.** Общая длительность сценария с подготовкой и завершением — 24,195 с. [Android-лог](logs/LockdownColdStartReviewTest.log), [logcat](logs/LockdownColdStartReviewTest-logcat.txt), [JSON с состояниями и обменом](logs/lockdown-cold-start-review.json).

| Наблюдение | После холодного запуска | После `recheck()` |
|---|---|---|
| Системный lockdown | true | true |
| Кэшированное состояние в приложении | false | true |
| Фактические исключения VPN | `com.v2ray.ang` | пусто |
| UID прокси | `-3` / UID_NONE | `10118`, UID установленной v2rayNG |
| Запуск текущего engine | `1794723236463` | `1794723242101` |
| Подтверждение захвата | `1794723239490` | `1794723243471` |
| HTTP через прокси | пустой ответ, точного payload нет | точный ответ получен |
| UDP через прокси | до recheck в этом сценарии не отправлялся | точный ответ получен |

До recheck тестовый TCP-сокет имел источник `10.111.0.1`: запрос уже направлялся в VPN, но работоспособный путь через ошибочно исключённый прокси не обеспечивался. Чтение завершилось пустым ответом за 1848 мс; это не истечение пятисекундного ограничения теста. После прямого вызова существующего `FirewallService.recheck()` на главном потоке появился новый интерфейс с правильным списком, и точные TCP/UDP-ответы были получены. Успешно проверены записи исходного приложения с `via=proxy` и собственные прямые записи v2rayNG к LAN-ответчику: TCP 91/216 байт, UDP 35/49 байт.

Этот результат подтверждает конкретный сбой доступности и восстановление кодовым путём, который UI вызывает при `onResume`. Отдельный пользовательский жест возврата в UI в данном сценарии не автоматизировался. Периодическое автоматическое восстановление без `recheck()` и его задержка здесь не измерялись.

Область вывода — Android 10/API29, официальный v2rayNG2.3.11 в Proxy only и локальный тестовый профиль. Исходящие назначения профиля относятся к LAN; удалённый VPN-сервер и Android 14/15 этой проверкой не подтверждены. Поведение системного запрета при полностью остановленном VPN проверяется отдельно и не выводится из описанного дефекта конфигурации.
