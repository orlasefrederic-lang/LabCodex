# DNS audit — NetStrazh 1.1.12

The original UDP hostname sticky-refusal problem no longer reproduces on Android 10, and the two earlier DnsPipe deadline overruns no longer reproduce in bounded local JVM probes. A new UDP policy-change regression is confirmed in two Android scenarios: existing DNS sessions keep the app/DNS decision captured when created and forward newly disallowed queries. The TCP hostname fix is present in source, but both first-run Android TCP probes failed at connection setup before sending a DNS payload, so their runtime filtering result remains unestablished.

Source compared: 1.1.12 against `/workspace/netstrazh-v1.1.10-review/sources/netwatch/Lab-claude-confident-cray-n5kkx8/NetStrazh`. App source files were read/compiled unchanged. Diagnostic files are outside the source tree. This branch used no Gradle or ADB operations and no external DNS/network traffic. JVM probes used bounded loopback sockets and OpenJDK 21. Runtime/environment instructions were read, and the environment/network policy inspected without exposing credentials.

## Original findings and fixes

**UDP sticky hostname refusal — fix confirmed on Android.** UdpRelay.kt:106 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/UdpRelay.kt:106`) now evaluates the hostname rule for each datagram. A domain rejection no longer becomes the permanent decision for every name on that socket. UdpRelay.kt:197 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/UdpRelay.kt:197`) creates a `NOPATH` session for the first rejected name; the next allowed name at :120 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/UdpRelay.kt:120`) clears the blocked marker and opens the upstream path. The distinct `refuseAll` state represents app-wide DNS rejection. The [t01 result](logs/DomainRegressionTest.log#L14) passes the original blocked-name then allowed-name scenario. [The recorded traffic](logs/runtime-early-logcat.txt#L3) shows `allowedRcode=0, allowedForwarded=true`; the test also verifies REFUSED and no forwarding for the blocked name. The source test `E2eTest.t12` covers the same fixed-policy scenario.

**TCP hostname bypass — source fix present; first Android probes inconclusive.** Engine.kt:418 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:418`) reads the two-byte length and the complete message through `readExactly`; the loop at :416 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:416`) supports repeated framed messages on one connection. Engine.kt:426 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:426`) calls `dnsRefusal(uid, name)` for every message before forwarding it. Refused replies are framed and returned locally; allowed replies follow the selected proxy/direct resolver route. readExactly():487 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:487`) handles incomplete reads. This addresses the old bypass for ordinary single-question DNS queries through the configured fake resolver address in source. It does not establish filtering of encrypted DNS or arbitrary third-party DNS endpoints. Prepared `DomainRegressionTest.t02` repeats the old TCP bypass case; `t05` uses one connection for blocked→allowed→blocked names, writes the length bytes and body in separate pieces, and checks that the controlled resolver sees only the allowed name. TCP can coalesce application writes, so the test creates opportunities for partial reads without proving a specific kernel segmentation. In the first Android run, [t02 failed while connecting the allowed control query](logs/DomainRegressionTest.log#L27), and [t05 failed while opening its client connection](logs/DomainRegressionTest.log#L130), both with `ECONNREFUSED` at `10.111.0.53:53`. Neither sent a DNS message. These errors neither confirm the TCP filtering fix nor demonstrate a surviving hostname bypass. Intermittent TCP connection refusal was also observed during the 1.1.10 review; its cause and relevance need separate investigation.

**DnsPipe common deadline — confirmed locally.** DnsPipe.kt:45 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/DnsPipe.kt:45`) derives one deadline from `System.nanoTime()`, recomputes the remaining time after opening, and passes a remaining-time function to send. DnsPipe.kt:134 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/DnsPipe.kt:134`) uses timed `ReentrantLock.tryLock`; the write deadline at :141 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/DnsPipe.kt:141`) uses the remaining budget. close/fail at :189 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/DnsPipe.kt:189`) still closes without taking the write lock.

Scheduling/JIT overhead explains why wall times are approximate; the code comment “at most” is stronger than these JVM scheduling primitives can guarantee. Do not resurrect the old close-deadlock finding: close causes the permitted one-time query retry, so a query can remain alive after the original channel closes.

The fixed budget is `DnsPipe.query()`'s budget. Upstream.dnsQuery():375 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Upstream.kt:375`) may subsequently try a dedicated connection. Its connection, handshake and response stages retain separate limits (Upstream.kt:384 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Upstream.kt:384`)); these measurements do not prove a 3-second end-to-end limit for the entire fallback chain.

## New UDP rule-change regression

**Status: reproduced twice on Android 10 with controlled local DNS; source explains the failures.** UdpRelay.kt:110 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/UdpRelay.kt:110`) now checks `s.refuseAll` and the current hostname rule. `refuseAll` is set only when creating the session (UdpRelay.kt:190 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/UdpRelay.kt:190`)). This omits the previous per-datagram `eng.dnsRefusal(uid, name)` check for the current app/DNS setting. FirewallService.onRulesChanged():194 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/FirewallService.kt:194`) normally calls `Engine.enforceRules`; Engine.kt:618 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:618`) excludes DNS connections, and UdpRelay.reevaluateBlocked():449 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/UdpRelay.kt:449`) only closes a blocked session if its UID is now allowed. Neither refreshes the captured `refuseAll` decision.

Deterministic reproduction, [DomainRegressionTest.t04](test-src/lab/netstrazh/DomainRegressionTest.kt#L284):

1. Block the source app, leave `blockDns=false`, and globally block one unique hostname.
2. Query that hostname on a UDP socket. It returns REFUSED locally and leaves a `NOPATH` session with `refuseAll=false`.
3. Enable `blockDns`. Verify that a new socket gets REFUSED for an otherwise allowed control name.
4. Send a different allowed hostname on the original socket. The existing session skips the new app/DNS policy, moves from `NOPATH` to `PENDING`, and opens an upstream path.

[DomainRegressionTest.t03](test-src/lab/netstrazh/DomainRegressionTest.kt#L236) additionally reproduces the issue with an allowed flow whose first response is held by the local fixture: after the resolver has seen that first request, block the UID and enable `blockDns`, check a fresh-socket REFUSED control, then ask a new name on the existing socket. The response hold is bounded and is always released. A fixture timing assertion keeps the policy change within the existing pipe query's 3-second deadline. Normal answered DNS sessions close at UdpRelay.kt:395 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/UdpRelay.kt:395`), so the in-flight version requires a pending response; the `NOPATH` version does not. DNS idle expiry is 20 seconds (UdpRelay.kt:464 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/UdpRelay.kt:464`)), but it is an idle limit, not a reason to regard the captured policy as fresh.

Both tests passed their fresh-socket REFUSED controls, then observed the newly blocked name at the controlled resolver and received `RCODE=0` on the retained socket. [t03's failure](logs/DomainRegressionTest.log#L76) is `new app/DNS policy must apply to existing UDP flow; responseRcode=0` at [the forwarding assertion :271](test-src/lab/netstrazh/DomainRegressionTest.kt#L271); [the runtime record](logs/runtime-early-logcat.txt#L61) explicitly states `forwarded=true rcode=0`. [t04's failure](logs/DomainRegressionTest.log#L103) is `enabling blockDns must prevent an existing NOPATH flow from starting an upstream path; responseRcode=0` at [the forwarding assertion :308](test-src/lab/netstrazh/DomainRegressionTest.kt#L308). These are two observed forms of the same defect, not two separate vulnerabilities.

Practical consequence: enabling “block DNS with app” or changing an app/network block need not affect the next query on a retained UDP DNS flow, although new flows apply the rule. This is distinct from the corrected hostname sticky-refusal problem and does not require a malicious app. Recommend evaluating `Rules.blockDns && Rules.isBlocked(uid, currentNetwork)` for every DNS datagram, followed by the current hostname decision, instead of treating captured `refuseAll` as authoritative. Reusing `eng.dnsRefusal(uid, name)` with the corrected per-query hostname state is one option. Update or close affected retained sessions when policy changes, including enabling/disabling DNS blocking and network-specific UID policy. Keep the new fixed-policy and mid-flow-policy tests.

## Additional static limitations

These were not reproduced as device failures and should remain separate from the confirmed JVM fixes and Android UDP policy defect.

**Direct TCP resolver reconnect/fallback.** Engine.kt:440 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:440`) reuses a direct upstream TCP channel, but any `IOException` sets `tcpRefused=true` for the entire app-side connection (Engine.kt:443 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:443`)). A routine resolver idle-close or timeout therefore has the same effect as lack of TCP support: subsequent messages never try a fresh TCP channel. udpDnsQuery():474 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:474`) returns a received UDP response unchanged, including a response with the truncation bit. The constructed scenario is a persistent client TCP connection, a resolver that closes the old upstream after one answer but supports fresh TCP, and a later answer too large for UDP. The client may receive a truncated reply over TCP while fresh upstream TCP would work. No controlled resolver reproduction was run for this scenario. Recommend retrying one fresh direct TCP channel before declaring TCP unavailable and explicitly handling truncation in the UDP fallback.

**DNS TCP idle cleanup gap.** These connections are tagged `proto="DNS"` at Engine.kt:334 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:334`). Reads at Engine.kt:418 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:418`), body read :422 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:422`), and response writes :460 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:460`) have no client-side deadline. The new two-hour idle sweep checks only `proto=="TCP"` at Engine.kt:628 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:628`). DNS TCP connections can therefore retain their thread/channel and relay slot indefinitely while silent, despite the new overall 2,000-relay admission cap. No exhaustion or two-hour waiting experiment was attempted. Recommend including DNS TCP in idle cleanup and bounding incomplete frame/read/write waits.

**DNS TCP failure notes.** Engine.kt:423 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:423`) increments transmitted bytes before obtaining a resolver answer. The enclosing error handler records a failure note only when both counters are zero (Engine.kt:396 (`NetStrazh/app/src/main/java/lab/netstrazh/vpn/Engine.kt:396`)). A failed lookup therefore usually leaves no explanatory connection note. This is a source-confirmed observability limitation, not a demonstrated filter bypass; use an explicit DNS failure note irrespective of already-counted query bytes.

## Android evidence and limits

[DomainRegressionTest.kt](test-src/lab/netstrazh/DomainRegressionTest.kt) remains outside the archive source tree. Its local SOCKS/DNS fixture never opens an external connection. `1.1.1.1` is only the intercepted SOCKS destination; replies are fixed TEST-NET data. Each new test uses unique names and transaction IDs; rule changes are restored in `finally`; the held response is released even when assertions fail. Root performed compilation/device execution. [The first complete run](logs/DomainRegressionTest.log#L217) reports five tests and four failures: one original UDP regression passes, two new UDP probes reproduce the same policy bug, and two TCP probes stop on connection refusal before payload. This is not a finding of four independent application defects. Results are scoped to that Android 10 emulator and the controlled local fixture.
