# NetStrazh 2.0: журнал, правила UID, ресурсы и границы компонентов

Проверен архив **`Netstrazh ver 2.0.zip`** из ветки `Netstrazh`, коммит
`5edab39c4301f45940155552a7e6dca868c63541`. SHA-256 архива:
`babd3eeb90b8c3cdb3f7c558641c720851c2ddea72f92b9dd2556631f5344883`.
Сравнение выполнено с исходниками ранее проверенного архива 1.1.15.
Этот документ описывает анализ исходников, не результаты Android-прогонов.
Пути строк ниже относительны корню `NetStrazh` внутри архива.

Модель использования: один владелец, доверенные приложения и ручные обновления.
В рассмотренной части **новой подтверждённой серьёзной проблемы не найдено**.
Старая гонка счётчика очереди исправлена; правила для неизвестного владельца
стали настраиваемыми. Поведение перезапуска VPN и DNS рассматривается отдельно.

## 1. Исправлено: очистка журнала больше не рассогласует отдельный счётчик очереди

В 1.1.15 `log()` отдельно увеличивал `AtomicInteger`, затем добавлял запись
в `ConcurrentLinkedQueue`; `clear()` отдельно очищал очередь и обнулял счётчик.
Это допускало отрицательное значение счётчика и превышение заявленного лимита.

В 2.0 используется **`LinkedBlockingQueue<Conn>(20_000)`** (`data/Db.kt:66`, `:139`),
`log()` вызывает неблокирующий `offer()` (`:75`), `flush()` — `poll()` (`:85`),
а `clear()` — `queue.clear()` (`:126`). Отдельный счётчик удалён. Согласованность
ёмкости теперь обеспечивает сама потокобезопасная ограниченная очередь;
старое чередование «зарезервировать в одном счётчике — очистить — добавить
в другую структуру» отсутствует.

**Статус:** исправление подтверждено изменённым путём исполнения в коде.
Старая JVM-модель двух отдельных структур больше не моделирует текущую
реализацию. Отдельный нагрузочный запуск оригинального Android `Db` этой
частью проверки не выполнялся; тестирование стандартной коллекции вместо
приложения не объявляется доказательством работы всей БД.

Осталось прежнее осознанное поведение: когда очередь заполнена, `offer()`
возвращает false, результат не отображается пользователю. Поэтому при перегрузке
журнал может терять строки без счётчика пропусков. Это не обход сетевого запрета;
для программы наблюдения полезно показывать число пропущенных записей.

## 2. Добавлено: правила для неизвестного UID и компонентов без пакета

`data/Rules.kt:87–96` вводит ключ `uid:<appId>`; для неизвестного владельца это
`uid:-1`. `flagsForUid()` (`:134`) и доменные правила (`:117`) теперь применяют
такие записи и к отрицательному UID. В 1.1.15 отрицательные UID всегда получали
нулевые флаги независимо от настроек.

Это **настраиваемая политика**, а не новый безусловный запрет: если владелец
не создал правило, `flagsForUid()` по-прежнему возвращает 0. Описывать 2.0 как
«неизвестный UID теперь всегда блокируется» было бы неверно.

Экран владельца соединений сохраняет правило по пакету либо `keyForUid`
(`ui/AppActivity.kt:144–155`). Для системных UID при добавлении запрета показывается
подтверждение (`:157–162`); собственный UID Стража блокировать из этого экрана нельзя.
Исключение из VPN требует реального пакета (`:145`, `:179–181`), а список исключений
дополнительно отбрасывает UID-ключи (`Rules.kt:132`). Строка вида `uid:-1` поэтому
не превращается в ошибочное `addDisallowedApplication`.

TCP при включённом запрете неизвестных владельцев делает до 10 дополнительных
lookup с интервалом 20 мс (`vpn/Engine.kt:356–366`, `:700`), чтобы не заблокировать
уже созданный сокет только из-за краткой задержки определения владельца. Это
улучшение доступности; окончательное решение всё равно зависит от текущих правил.
UDP сохранил предыдущие повторные lookup и ограничение их числа. Реальную гонку
атрибуции UID здесь не воспроизводили; проверка кода не доказывает, что Android
всегда отдаёт правильный UID.

## 3. Усилены две границы сетевой обработки

- **Wildcard TCP listener:** принятый сокет теперь должен иметь не только
  фиктивный peer-адрес и порт живой непринятой NAT-записи, но и локальный адрес
  самого TUN (`vpn/Engine.kt:313–319`). Добавлена нормализация IPv4-mapped IPv6
  (`:716–718`). Это закрывает ранее предложенную дополнительную проверку адреса
  назначения. В предыдущей версии открытый LAN-прокси не был доказан; новое
  условие следует описывать как усиление границы, а не исправление доказанного
  открытого прокси.
- **DNS TCP:** запись полного ответа клиенту, как и чтение запроса, получила
  deadline 30 секунд (`Engine.kt:453`, `:506`, `:705`). Клиент, переставший читать
  ответ, больше не должен удерживать этот write бессрочно. Это подтверждение
  наличия ограничителя по коду; заполнение буферов/истощение слотов в этом аудите
  не выполнялось. Подробности DNS и общего upstream-бюджета — в отдельном отчёте.

## 4. Что сохранилось и не следует выдавать за новые уязвимости

- Манифест идентичен 1.1.15. `allowBackup=false`; внутренние экраны не экспортированы;
  VPN-сервис требует системное разрешение `BIND_VPN_SERVICE`. Новых компонентов,
  предоставляющих внешнему приложению доступ к правилам или журналу, нет.
- Настройки и правила остаются в `MODE_PRIVATE`, журнал в приватной SQLite БД.
  Поиск журнала передаёт введённый текст SQL-параметрами (`Db.kt:153–156`).
  Подстановка UID и лимитов использует типизированные числа; нового SQL-ввода
  произвольной строки не найдено.
- TCP имеет прежний настроенный предел 1024 relay (`Engine.kt:698`) и cached pool
  (`:97`). Обычное двунаправленное реле может занимать два потока (`:425`). Это
  существенно ограниченное число соединений, но не малый измеренный бюджет
  потоков/памяти для слабого телефона. Нагрузочное падение не демонстрировалось.
- UDP по-прежнему ограничен 4096 сессиями, 32 ожидающими пакетами на сессию и
  ограниченным исполнителем открытия соединений (`UdpRelay.kt:60`, `:460–464`).
- Предел журнала 300 000 строк остаётся периодической очисткой (`Db.kt:118`, `:138`),
  запускаемой при старте и раз в 6 часов (`FirewallService.kt:406`). Это не жёсткий
  предел размера SQLite-файла. Длительный flush всё ещё может задержать задания
  того же исполнителя. Это прежние ограничения, без нового нагрузочного доказательства.
- Хранение ключа подписи не менялось. Согласованную оговорку про ключ в репозитории
  и доверенные ручные обновления не следует повторно выдавать за новый дефект 2.0.

Главный экран теперь показывает «Проверяю, что трафик идёт через Стража…» до
`captureVerifiedAt >= Live.startedAt` (`ui/MainActivity.kt:159`, `:175`). Это
исправляет преждевременное сообщение о готовности, но текст UI сам по себе
не блокирует пакеты; сетевой эффект оценивается динамическими тестами отдельно.

## 5. Нельзя собирать старую папку ветки вместо проверенного ZIP

По SHA-256-манифестам архивов: **43 файла не изменились, 14 изменились, 2 добавлены**
(`VERSION` и `UpstreamDeadlineTest.kt`), удалённых нет. Всего в архиве 59 файлов.
[Список сравнения архивов](resource-audit/archive-source-comparison.json).

Архив 2.0 по-прежнему **не совпадает** с распакованной папкой проекта в том же
коммите ветки. Для 57 файлов внутри `NetStrazh`: **27 совпали, 26 различаются,
4 отсутствуют** в папке ветки: `.gitignore`, `VERSION`, `net/Hosts.kt` и
`vpn/UpstreamDeadlineTest.kt`. [Пофайловое сравнение](resource-audit/loose-source-comparison.json).
Выводы относятся к ZIP; сборка из старой папки может не содержать исправлений.

Номер, видимый пользователю, теперь берётся из `VERSION` (`app/build.gradle.kts:9`,
`:20`), а `versionCode` всё ещё равен `100 + BUILD_NUMBER` (`:8`, `:19`). При обычной
ручной сборке без BUILD_NUMBER получится code100; обновление уже установленного
APK с большим кодом потребует правильно заданного возрастающего номера сборки.
Это существующее соглашение versionCode, не новая уязвимость. Точные параметры
проверочной сборки и установка на эмулятор фиксируются в отчёте сборки.

Исходники приложения этим аудитом не изменялись. Новые JSON-файлы сравнения и
данный документ находятся вне дерева исходников.
