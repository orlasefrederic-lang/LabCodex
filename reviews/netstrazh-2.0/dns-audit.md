# NetStrazh 2.0: DNS, правила и сроки ожидания

Проверен неизменённый архив `Netstrazh ver 2.0.zip`, ветка `Netstrazh`, коммит
`5edab39c4301f45940155552a7e6dca868c63541`, SHA-256
`babd3eeb90b8c3cdb3f7c558641c720851c2ddea72f92b9dd2556631f5344883`.
Сравнение — проверенный архив 1.1.15. Пути к коду ниже начинаются внутри
`NetStrazh/app/src/main/java/lab/netstrazh/`.
Это отдельная часть аудита; Android-сценарии и общий вывод приведены в итоговом отчёте.

## Главное

**Прежнее суммирование полных тайм-аутов SOCKS исправлено.** Для числовых адресов
прокси и DNS повтор прежнего воспроизведения завершился около общего бюджета,
а не после суммы greeting + CONNECT. Успешный медленный CONNECT сохранился.
При этом синхронное разрешение имени ещё может пережить общий deadline;
выявлен небольшой новый путь без явного закрытия сокета при уже истёкшем deadline.
Оба остатка относятся к надёжности. Эти тесты не показали утечку сетевых данных
или обход запрета приложения.

## Проверенные исправления

### Общий бюджет greeting, CONNECT и DNS

`vpn/Upstream.kt:259–297` принимает монотонный абсолютный deadline.
`limitMs` (`:302–309`) вычисляет остаток перед connect, greeting, CONNECT и DNS.
`dnsQuery` (`:395–406`) перестал принудительно давать fallback ещё минимум1500мс
после истечения общего времени. `queryOnce` (`:415–426`) передаёт один deadline
через все сетевые этапы. Укороченный DNS-бюджет также больше не служит причиной
объявить приложение прокси «уснувшим» (`greet`, `:435–443`).

Повтор прежнего локального сценария на **неизменённых** Upstream/DnsPipe/Socks:

| Сценарий | 1.1.15 | 2.0 |
|---|---:|---:|
| Бюджет300мс; greeting220мс + CONNECT220мс | 493 / 443 / 443мс | **386 / 300 / 300мс** |
| Общий бюджет6000мс; pipeline ждёт3000мс, fallback greeting2200мс + CONNECT2200мс | 7410мс | **6003мс** |

Значение386мс первого запуска сохраняется, а не округляется до300: запуск JVM,
первое выполнение и планирование добавляют задержки. Это не гарантия жёсткого
реального времени; причина прежнего повторного использования полного бюджета
устранена по коду и двум прогретым коротким случаям/полному сценарию.

Материалы: [результат](audit-dns/upstream-deadline-result.txt),
[сценарий](audit-dns/UpstreamDeadlineAudit.kt), [запуск](audit-dns/run-upstream-audit.py).
Android-граница заменена малым EngineHost; `Engine.isLocal` в заглушке совпадает
с исходником. SOCKS fixture слушает loopback, наружу запросы не передаёт.

### Медленный CONNECT остаётся рабочим

Отдельный fixture сразу ответил на greeting, задержал CONNECT на7500мс,
затем точно обменялся данными: **7554мс до открытия**, 41байт запроса / 61байт ответа,
`viaProxy=true`, `proxyEvents=[]`, `downAt=0`, `lastError=null`.
Это проверяет сохранение исправления1.1.15: долгий CONNECT после быстрого greeting
не приравнивается к зависшему локальному прокси.
[Результат](audit-dns/slow-connect-result.txt), [сценарий](audit-dns/SlowConnectAudit.kt).

### DNS TCP теперь ограничивает и запись ответа

`vpn/Engine.kt:506` добавляет общий30-секундный `withDeadline` вокруг записи
полного DNS-фрейма клиенту. Чтение длины/тела следующего запроса уже было ограничено
на `:453`. Старый статический остаток «молчащий читатель может бессрочно удержать
поток на записи ответа» исправлен по коду. Нагрузочное удержание/истощение
сокетов на Android этим аудитом не выполнялось.

### Правила DNS и неизвестных владельцев

`UdpRelay.kt` полностью совпадает с1.1.15: каждый DNS-пакет проверяет текущую
политику через `eng.dnsRefusal` (`:113`). TCP делает проверку для каждого полного
запроса (`Engine.kt:466`). Старое поле с сохранённым решением при создании сессии
не вернулось. `Hosts.kt` и разбор DNS также не менялись. Результаты свежих
Android-регрессий нужно брать из основного отчёта, не из прошлой версии.

Старая формулировка «неизвестный UID всегда разрешён» для2.0 уже неверна:
`Rules.keyForUid` (`data/Rules.kt:87`) и `flagsForUid` (`:134`) поддерживают `uid:-1`,
а доменные правила используют тот же appId (`:117`). Без выбранного правила
разрешение по умолчанию сохраняется. Когда неизвестные владельцы заблокированы,
TCP делает до10 дополнительных lookup с шагом20мс (`Engine.kt:360`), прежде чем
применить итоговую политику. Это улучшение политики, а не обещание всегда
правильно определить владельца. Android10 системный DNS по-прежнему может
принадлежать UID системного резолвера. Намеренно разрешённый пользователем DNS
не считается дефектом.

## Остаток1: синхронное разрешение имени не отменяется по deadline

**Приоритет: небольшой/условный для конфигураций с именем прокси или DNS-сервера.**

`Upstream.proxyEndpoint` (`:116–122`) вызывает `host.resolve(c.host)` синхронно.
`dnsQuery` вызывает `host.resolve(cfg.dnsServer)` в fallback (`:404`); проверка
оставшегося времени после вызова отсекает дальнейшие шаги, но не прерывает сам
resolver. В Android это `Network.getAllByName` (`FirewallService.kt:338–343`),
без переданного caller deadline. Обычные числовые адреса проходят быстрым путём.

Ограниченный тест неизменённого Upstream с **намеренной задержкой только в
заглушке EngineHost.resolve**, без внешнего DNS:

- `dnsQueryOnce`, бюджет50мс, разрешение имени прокси250мс: возврат через**279мс**.
- Полный `dnsQuery`, общий бюджет6000мс; resolver спит4000мс в открывающей pipeline
  операции и4000мс в синхронном fallback (эти ожидания частично параллельны):
  возврат через**7002мс**, две операции resolve.

Это подтверждает условный путь выполнения сверх бюджета, **не измеряет сбой
реального Android DNS и не утверждает такую задержку при127.0.0.1/1.1.1.1**.
Исправление: заранее разрешённый/кэшированный адрес или отменяемая операция
разрешения с ожиданием только остатка общего срока. Проверка deadline после
синхронного resolve сама по себе не ограничивает длительность вызова.

## Остаток2: истечение срока после создания канала пропускает его закрытие

**Приоритет: низкий, управление ресурсом.**

`vpn/Upstream.kt:231` создаёт защищённый канал, затем `:232` вызывает `limitMs`.
Этот вызов расположен **до** `try`/`catch` (`:233–244`). Если deadline уже истёк
во время resolve, создания сокета или `protect`, исключение выбрасывается до
закрывающей ветки. `queryOnce` передаёт пустой tracker (`:418`), а его `finally`
закрывает только успешно возвращённый `Opened`. `Upstream.close()` этот
невернувшийся канал также не знает.

В том же bounded-сценарии записан созданный Socket только для проверки состояния:

- Бюджет50мс + разрешение имени250мс: создан1канал, после ошибки **isOpen=true**,
  после `Upstream.close()` **isOpen=true**.
- Бюджет50мс + намеренно задержанный `EngineHost.protect`250мс: тот же результат,
  метод вернулся через250мс.

Затем harness немедленно закрыл удерживаемую ссылку. Это доказывает отсутствие
детерминированного закрытия на данном пути; **не доказывает постоянную утечку
до конца процесса или истощение дескрипторов** — GC/cleaner может освободить
недостижимый канал. Тест не создавал большое число сокетов и не истощал ресурсы.
Исправление: проверить остаток до выделения канала и также закрывать канал при
любом исключении после выделения (поместить проверку limit в защищённый блок
с передачей владения только при успешном возврате).

Оба остатка: [результат](audit-dns/dns-boundary-result.txt),
[сценарий](audit-dns/DnsBoundaryAudit.kt), [запуск](audit-dns/run-boundary-audit.py).

## Прочие границы

После неудачного свежего прямого TCP DNS-подключения клиентская сессия всё ещё
переходит к UDP fallback; TC в UDP-ответе не инициирует новую TCP-попытку
(`Engine.kt:490–493`, `:512–521`). Это прежняя статическая оговорка надёжности
для крупных ответов после временного TCP-сбоя; отдельного воспроизведения нет.
Уже разрешённые и поставленные в очередь DNS-запросы при смене правила не
отзываются; актуальная проверка применяется к следующему принятому запросу.

Ни один тест этой части не требует удалённого сервера, личных ключей или
вредоносного приложения. Исходники приложения не изменялись; новые файлы
находятся только в `audit-dns/` и этом отчёте.
