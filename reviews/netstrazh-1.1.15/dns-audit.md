# NetStrazh 1.1.15 — DNS и применение правил

Проверка 4 ноября 2026. Сравнение исходников архивов 1.1.12 и 1.1.15. Исходники приложения не менялись. Корень путей ниже: `sources/Lab-claude-confident-cray-n5kkx8/NetStrazh/app/src/main/java/lab/netstrazh/`. Это специализированная часть проверки; результаты Android-тестов добавляются в основной отчёт отдельно.

## Исправления по исходному коду

1. **Смена политики на уже открытом UDP DNS-сокете теперь проверяется для каждого запроса.** `vpn/UdpRelay.kt:108–129` вызывает `eng.dnsRefusal(s.conn.uid, name)` каждый раз. Старое поле `Session.refuseAll` удалено. `Engine.dnsRefusal` (`vpn/Engine.kt:635–639`) проверяет текущее `Rules.blockDns`, блокировку UID на текущей сети и блокировку имени. Это устраняет причину обоих сценариев 1.1.12: уже активный поток и поток NOPATH после первого отказа имени больше не опираются на старое значение галочки. Создание заблокированного DNS-потока переводит его в NOPATH (`UdpRelay.kt:190–195`); разрешённый следующий запрос может запустить маршрут (`:123–128`). Статический вывод следует подтвердить теми же Android-регрессиями.
2. **Прежние исправления разных доменных имён сохранены.** UDP оценивает имя каждого запроса, TCP делает то же после каждого полного DNS-фрейма (`Engine.kt:458–468`). Одно заблокированное имя не должно навсегда запрещать другие имена на том же сокете. `Hosts.kt` не новый: SHA-256 в обоих архивах `1f359eb994f103b0c98161dceb445bebbbb49399e60cbb7948baba7465a09918`. Нормализация и проверка домена/поддоменов не менялись.
3. **Ограничено ожидание следующего/недописанного DNS TCP-запроса.** `Engine.kt:448–457` оборачивает чтение длины и тела запроса в общий 30-секундный `withDeadline`; при истечении времени канал закрывается. Константа `DNS_TCP_IDLE_MS` — `:698`. Это исправляет прежнее бессрочное удержание слота только молчащим или приславшим неполный запрос клиентом. Запись ответа отдельно обсуждается ниже.
4. **Переиспользованный прямой DNS TCP-канал получает свежую попытку.** `Engine.kt:477–488` после ошибки уже открытого канала закрывает его и пытается открыть новый; раньше любая ошибка переводила соединение клиента только на UDP. Если и новый канал не работает, остаётся UDP fallback. Это улучшение надёжности, а не доказательство корректной работы со всеми резолверами.
5. **Ожидание SOCKS greeting отделено от ожидания CONNECT.** `Upstream.kt:265–271` использует короткий лимит только для greeting локального прокси. CONNECT получает обычный лимит. **Подтверждено отдельным локальным JVM-тестом на неизменённых Upstream/Socks/DnsPipe:** мгновенный greeting, задержка CONNECT 7500 мс (прежний локальный лимит — 6000 мс), успешное открытие за **7525 мс**, `viaProxy=true`, точная передача 41 байта и точный ответ 61 байт. `proxyEvents=[]`, `downAt=0`, `lastError=null`: медленный CONNECT не назван уснувшим/зависшим прокси. Фиктивный сервер работает только на loopback, к TEST-NET-назначению не подключается. [Результат](audit-dns/slow-connect-result.txt), [сценарий](audit-dns/SlowConnectAudit.kt), [запуск](audit-dns/run-slow-connect-audit.py). Цена этой реализации — общий DNS-бюджет всё ещё складывается из отдельных этапов, см. подтверждённый остаток ниже.

## Подтверждено локальным воспроизведением: новый общий DNS-бюджет не ограничивает всю операцию

**Приоритет: средний для надёжности; утечка или обход правил этим тестом не показаны.**

`Upstream.dnsQueryOnce` (`vpn/Upstream.kt:391–399`) вычисляет общий deadline, но сначала вызывает `openTcp(..., handshakeMs = budgetMs)`. Внутри `openTcp` SOCKS greeting и CONNECT получают **каждый полный budgetMs** (`:265–271`), а подключение к самому прокси (`:220–248`, socket connect на `:232`) не ограничено оставшимся DNS-бюджетом. Только после них оставшееся время используется для самого DNS-запроса. Если greeting и CONNECT по отдельности укладываются в лимит, их сумма может его превысить. Общее `dnsQuery` (`:379–388`) тем самым тоже не укладывается в заявленные «около DNS_TOTAL_MS»; после истечения общего времени оно дополнительно гарантирует fallback не меньше 1500 мс. Разрешение имени `cfg.dnsServer` выполняется после вычисления `left` (`:386`) и также не входит в переданный остаток.

**Воспроизведение:** JVM компилирует неизменённые `Upstream.kt`, `DnsPipe.kt` и `Socks.kt` прямо из архива. Подменена только граница Android `EngineHost`/константа протокола; `Engine.isLocal` скопирован дословно. SOCKS-сервер слушает только `127.0.0.1` и не выполняет запросов наружу. Адрес `198.51.100.10` используется только в фиктивном запросе SOCKS.

- `dnsQueryOnce` с бюджетом 300 мс: сервер отвечает на greeting через 220 мс, затем на CONNECT ещё через 220 мс. Три результата: **493, 443, 443 мс**. Все завершаются DNS IOException уже после бюджета.
- Полное `dnsQuery`: первая pipeline-попытка ждёт 3000 мс; новая fallback-сессия получает greeting через 2200 мс и CONNECT ещё через 2200 мс. Общая операция длится **7410 мс** при `DNS_TOTAL_MS = 6000`.
- Лишнее время объясняется двумя явными задержками протокола, а не только небольшим шумом планировщика. При обычном быстром greeting это не обязательно заметно. Замедленный/зависший прокси может вызвать лишнее ожидание и повторы DNS у Android.

Материалы: [результат](audit-dns/upstream-deadline-result.txt), [сценарий](audit-dns/UpstreamDeadlineAudit.kt), [сборка и запуск](audit-dns/run-upstream-audit.py), [граница Engine](audit-dns/EngineStubs.kt), [константа Android](audit-dns/AndroidConstantsStub.kt).

**Исправление:** один монотонный абсолютный deadline для всей цепочки. На каждом этапе вычислять положительный остаток: разрешение адреса, TCP connect/retry grace, greeting/login, CONNECT, DNS write/read. Если остаток исчерпан, не начинать новую попытку. Для асинхронного разрешения имени нужна отменяемая/ограниченная операция или заранее разрешённый адрес. Передавать deadline в `openTcp`/`proxyChannel`, а не использовать одно и то же `budgetMs` заново для каждого handshake.

## Остатки и границы выводов

- `Engine.kt:499–501` всё ещё пишет DNS TCP-ответ клиенту без deadline. Новый 30-секундный лимит охватывает только чтение запроса. Клиент, который продолжает отправлять запросы и не читает ответы, после заполнения TCP-буферов может удерживать поток/слот на записи. Это **статический остаток**, не выполненная атака и не измеренное истощение ресурсов; типичные маленькие DNS-ответы сами по себе не означают, что запись сразу блокируется. Общий лимит TCP-сессий теперь 1024 (`:693`), поэтому нельзя говорить о неограниченном числе сессий. Практическая рекомендация — ограничить также запись полного фрейма.
- После неудачной свежей попытки прямого TCP-резолвера `tcpRefused` остаётся true до конца клиентского соединения (`Engine.kt:444,486`). UDP fallback не обрабатывает TC как необходимость ещё одной TCP-попытки (`:489,507–516`). Это оставшаяся гипотеза надёжности для большого ответа после временного TCP-сбоя, не новая подтверждённая утечка.
- UDP DNS-запрос, который уже прошёл проверку и попал в очередь до смены правил, не отменяется автоматически: очередь отправляется в `UdpRelay.kt:289–295`, async DNS разрешается в `:299–318`. Новый код гарантирует проверку **следующего принятого запроса**; это не равнозначно отзыву уже разрешённой операции. Не считать это повторением старого бага без отдельного согласованного требования отменять запросы «в полёте».
- UDP-пакеты к объявленному DNS `10.111.0.53:53` получают описанную DNS-политику. Произвольный сторонний DNS, DoH/DoT, неизвестный UID и отсутствие имени в шифрованном трафике — прежние ограничения архитектуры; они не изменены в этой версии. На Android 10 системный DNS может принадлежать UID резолвера, что уже явно оговорено в README. Проверка учитывает личное использование и отсутствие намеренно вредоносных приложений.
- Изменения очередей/разбора DNS/`DnsPipe`/`Hosts` отсутствуют. Старые результаты тестов нельзя выдавать за свежий запуск 1.1.15. Этот отчёт даёт новый JVM-результат для таймаута; результаты Android-прогонов принадлежат основному отчёту.
