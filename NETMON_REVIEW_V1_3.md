# Проверка Netmon 1.3

Дата: 2026-11-08.

## Итог

Два конкретных замечания из [отчёта по 1.2](NETMON_REVIEW_V1_2.md) закрыты изменениями в исходниках. Найдена **одна новая пограничная ошибка P2**: явный запуск нового владельца PID может быть проигнорирован, если он произошёл вскоре после первого наблюдения старого процесса. При этом старый процесс уже явно завершён. Новые байты могут учитываться у него.

Первоначально ревью было статическим: исполнитель не принимал команды. Позже 2026-11-08 среда восстановилась, и проверка дополнена реальным запуском на Linux с Python 3.12.14 и PowerShell 7.4.13. **Все 102 штатных теста прошли без пропусков; V13-1 воспроизведён дополнительными тестами.** GUI, реальные ETW и Windows Firewall не запускались. Частота описанного повторного использования PID на реальной Windows не измерялась.

## V13-1 — P2: запуск после явного завершения сливается с завершённой записью

**Место:** model.py:391–405, функция _apply_start; дальнейшее неверное начисление трафика — _instance_at, строки 349–359.

В версии 1.2 объединение нового события запуска с уже имеющейся записью требовало cur.ended is None. В 1.3 это условие исчезло. Теперь достаточно, чтобы cur.first_seen >= ts - CLOCK_EPS, где CLOCK_EPS = 0.05.

Если известна последовательность «старый процесс запущен → старый завершён → новый запущен», допуск времени всё равно может заставить код проигнорировать последний запуск. Ни явно заполненное время завершения, ни другое имя программы этому не препятствуют.

### Минимальный пример

После распаковки, из каталога netmon:

~~~python
from model import Model

m = Model()
m.resolve_names = False
m.on_process_start(100, 100.00, r'C:\old.exe')
m.on_process_stop(100, 100.01)
m.on_process_start(100, 100.02, r'C:\new.exe')
m.on_traffic(
    100, 'TCP', True, 9,
    '1.1.1.1', 443, '10.0.0.1', 50000, 100.03,
)
m.process_pending()

print([(p.name, p.started, p.ended, p.sent)
       for p in m.procs.values()])
~~~

**Фактический результат запуска минимального примера на Python 3.12.14:**

~~~text
[('old.exe', 100.0, 100.01, 9)]
~~~

**Ожидается:**

~~~text
[('old.exe', 100.0, 100.01, 0),
 ('new.exe', 100.02, None, 9)]
~~~

### Почему это происходит

1. Первый start создаёт old.exe с first_seen = started = 100.0.
2. Stop выставляет ended = 100.01.
3. Второй start проходит условие 100.0 >= 100.02 - 0.05.
4. Старые path и started уже заполнены, поэтому код ничего не меняет и возвращается. new.exe не создаётся, by_pid[100] продолжает указывать на завершённый old.
5. Для пакета в 100.03 точного попадания нет. Запас после завершения допускает 100.03 <= 100.01 + 0.25, поэтому 9 байт получает old.

Тот же дефект есть, если новый процесс запускает **тот же exe**. Проверка только несовпадающих путей не исправит весь случай.

Это отличается от уже описанного в README ограничения, когда пакет нового процесса приходит раньше события о его запуске: здесь событие запуска приходит **до пакета**, но программа его отбрасывает.

### Последствия и приоритет

При столь быстрой смене владельца PID история процессов и счётчики становятся неверными; действующий процесс может временно отображаться как завершённый или отсутствовать отдельной строкой. Дефект не означает автоматического создания ошибочного правила брандмауэра.

Приоритет P2: конкретная ошибка обработки известной последовательности событий, но частота такого интервала повторного использования PID на Windows не установлена.

### Что исправить

- Не объединять новый start с экземпляром, который явно завершился до времени этого start.
- Отдельно учитывать действительно запоздавший start старого экземпляра, чтобы исправление не создавало лишних записей при задержке событий.
- Совпадение времени в пределах CLOCK_EPS не должно отменять уже известную последовательность stop → start.
- Добавить проверки с разными и одинаковыми exe, интервалом меньше 0,05 с и трафиком после второго start. Одного уменьшения допуска недостаточно.

В [NETMON_REVIEW_V1_3_CHECKS.py](NETMON_REVIEW_V1_3_CHECKS.py) подготовлены пять тестовых методов: прежние сценарии 1.2 и два аспекта V13-1. Assertions описывают **правильное ожидаемое поведение**. Скрипт выполнен на исходной 1.3: первые три метода прошли, последние два выявили V13-1. Unittest сообщает failures=3, потому что один из этих двух методов содержит два падающих subtest: с другим и с тем же exe.

Фактические несовпадения:

~~~text
Ran 5 tests in 0.001s
FAILED (failures=3)

Создан 1 экземпляр вместо 2 — для обоих путей exe.
Трафик: {'old.exe': 19} вместо {'old.exe': 10, 'new.exe': 9}.
~~~

## Остальные изменения

- etw.py:499: ClientContext переключён с QPC (1) на системное время (2). Существующее преобразование FILETIME в _timestamp совместимо с этим: режим ProcessTrace не включает RAW_TIMESTAMP. Отдельной конкретной регрессии в этом изменении по коду не найдено. Поведение при корректировках системных часов требует проверки на Windows.
- winapi.py:508–513: добавлено преобразование обычных MUP/LanmanRedirector путей в UNC; соответствующие примеры добавлены в тесты. Исполнение Windows API здесь не проверено.
- Код брандмауэра не изменён относительно 1.2; его штатные тесты повторно прошли в составе 102 тестов. Это не проверка реального прохождения/блокировки пакетов Windows.

## Как завершить проверку после исправления

Из распакованного каталога netmon:

~~~bat
python -m unittest discover -s tests -v
~~~

Проверочный скрипт можно держать отдельно; аргумент — каталог с model.py:

~~~bat
python NETMON_REVIEW_V1_3_CHECKS.py "C:\путь\к\netmon"
~~~

Проверочный скрипт использует только модель и стандартную библиотеку, не меняет брандмауэр и не отправляет сетевые запросы.

Для окончательного подтверждения основной функции нужен прогон на Windows: наблюдение реальных процессов и трафика, запрет выбранного тестового exe, проверка отсутствия соединений, временное разрешение и повторное включение запрета. В этой сессии этот этап не выполнен.

Исходники приложения и архивы при ревью не изменялись.
