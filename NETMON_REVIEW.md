Проверка Netmon.zip — заключение для исправления кода

Дата: 28 октября 2026 года.

Программа: монитор сетевых подключений для Windows на Python, с историей SQLite и управлением правилами Windows Firewall.

Проверен файл `Netmon.zip` из репозитория `orlasefrederic-lang/LabCodex`. SHA-256 архива: `b7e368bf638ed8dd32a47fa18a8166512da5ec2962f5fed01c7b40795a2b6f3d`. Git blob: `76193c58d71ca7e5b203ef78f42f62f8969e596a`.

Все пути и номера строк ниже относятся к каталогу `Lab-claude-exciting-rubin-7ydofi/netmon` внутри этого архива. После изменения файлов ориентироваться также на названия функций. Исходный код при аудите не изменялся.

**Общий вывод**

Архитектура в целом разумная: сбор событий Windows ETW, модель данных, SQLite, интерфейс и управление файрволлом разделены по модулям. Однако обнаружены воспроизводимые ошибки. Наиболее существенная: при неудачном изменении запрета могут исчезнуть действующие правила, а интерфейс продолжит показывать «запрещена». До исправления и интеграционной проверки на Windows такую надпись нельзя считать надёжным подтверждением блокировки.

В просмотренном коде не обнаружено очевидной скрытой отправки истории на сторонний сервер. Присутствуют ожидаемые DNS-запросы для определения имён и открытие ipinfo.io по команде пользователя. Это наблюдение по исходникам, а не гарантия отсутствия любых уязвимостей.

**Что было проверено и что не проверено**

- Все 51 штатный тест прошли: `python -m unittest discover -s tests -v`.
- Для трёх тестов PowerShell использовался PowerShell 7.4.13 под Linux с тестовыми заменами командлетов Windows Firewall. Остальные 48 тестов прошли и без PowerShell.
- Проверен синтаксис 15 Python-файлов на совместимость с грамматикой Python 3.8. Это не равно запуску приложения на Python 3.8.
- Демо-монитор запущен; подтверждены обработка событий и сохранение истории при остановке.
- Отдельными диагностическими сценариями проверены ошибки ниже, не охваченные штатными тестами.
- Настоящая Windows не запускалась. Не проверены живые события ETW, UAC, Windows PowerShell 5.1 и фактическое блокирование пакетов правилами NetSecurity. Успех тестов с заглушками не является подтверждением работы этих механизмов на Windows.

**1. Высокий приоритет: при неудачном обновлении запрета удаляется действующая защита**

Места: `firewall.py:215–220` (`_ADD_BODY`), `firewall.py:400–404` (`FirewallManager.block`), `firewall.py:423–442` (`FirewallManager._run`). Аналогичный порядок действий в CLI: `console.py:130–133`.

Причина: сначала удаляются прежние правила, затем создаются новые. При ошибке создания отката нет. После ошибки менеджер также не перечитывает состояние правил и оставляет прежний кэш.

Воспроизведение с настоящим PowerShell и тестовыми командлетами:

1. Создать запрет для тестового exe в обоих направлениях: два правила.
2. Повторить запрет, выбрав только исходящее направление.
3. При создании нового правила вернуть ошибку «Отказано в доступе».
4. Фактически остаётся ноль правил. Менеджер возвращает статус `('blocked', 'запрещена')`.

Сообщение об ошибке пользователю показывается, но прежняя блокировка уже потеряна, а надпись в таблице устарела.

Рекомендуемое исправление: сохранять прежнюю защиту до успешного изменения; существующие правила по возможности обновлять, а лишние удалять последними. Для частичных сбоев предусмотреть восстановление прежнего состояния. После любой попытки изменения перечитывать правила; если состояние прочитать невозможно, показывать «неизвестно», а не «запрещена».

Регрессионная проверка: ошибка создания/изменения одного из правил не снимает прежний запрет; сообщение об ошибке и отображаемое состояние соответствуют фактическому результату. Проверить GUI и CLI.

**2. Средний приоритет: отказ удаления правила выдаётся за успешное снятие запрета**

Места: `firewall.py:225–227` (`_REMOVE_BODY`), `firewall.py:435–436`.

Причина: `Remove-NetFirewallRule -ErrorAction SilentlyContinue` подавляет не только отсутствие правила, но и другие нетерминирующие ошибки. Скрипт затем безусловно возвращает успех. Перечитывание списка не используется для проверки, что нужные правила действительно исчезли.

Воспроизведение: создать два правила, при удалении выдавать `Write-Error 'Access denied removing rule'`. Оба правила остаются, `manager.error` пустой, сообщение пользователю — «Убрано из списка».

Рекомендуемое исправление: отдельно обрабатывать ожидаемое отсутствие правила, остальные ошибки передавать вызывающему коду. Подтверждать удаление по фактическому состоянию. Не выводить сообщение об успехе при сохранении выбранных правил.

Регрессионная проверка: отказ в доступе сохраняет правила и приводит к сообщению об ошибке; повторное удаление уже отсутствующего правила обрабатывается отдельно.

**3. Средний приоритет: при повторном использовании PID история и путь могут приписываться другой программе**

Места: `model.py:475–503` (`pending_details`, `fill_details`), `monitor.py:161–163` (`_fill_details`). Путь из модели затем используется интерфейсом для ручной блокировки.

Причина: подробности процесса запрашиваются по PID, который Windows может уже выдать новому процессу. Возвращённое время создания не сверяется с экземпляром процесса в модели. `pending_details()` может включать завершённые процессы; `fill_details()` переписывает имя, путь и время запуска без проверки соответствия.

Воспроизведение на модели:

1. Процесс old.exe с PID 100: запуск в момент 1, 10 байт трафика, завершение в момент 3.
2. PID 100 уже принадлежит new.exe, запущенному в момент 4.
3. Передать в `fill_details()` старой записи сведения new.exe.
4. Старая запись становится new.exe: запуск 4, завершение 3, трафик 10 байт.

Последствие: неверные имя, история и путь exe. Пользователь может вручную заблокировать программу, которой этот трафик не принадлежал.

Рекомендуемое исправление: идентифицировать экземпляр по PID и времени создания; отбрасывать несовместимые сведения, не перезаписывать ими завершённую запись. Учесть гонку между получением списка PID и чтением подробностей.

Регрессионная проверка: подробности нового владельца PID не меняют имя, путь и счётчики старого экземпляра; не возникает запись с началом позже завершения.

**4. Средний приоритет: при ошибке сохранения теряются удаления и остаются дубли истории**

Места: `monitor.py:165–173` (`_flush`), `model.py:606–637` (`collect_dirty`, `mark_dirty`), особенно строка 627.

Причина: `collect_dirty()` забирает очередь удалений `_deleted`. Если `Storage.save()` завершается ошибкой, возвращаются только признаки изменения процессов; очередь удалений не восстанавливается.

Воспроизведение:

1. Сохранить запись процесса в истории.
2. В новом запуске создать и сохранить временную запись того же работающего процесса до получения подробностей.
3. После получения подробностей объединить записи через `_reattach()`; лишняя запись ставится на удаление.
4. Первое сохранение после объединения искусственно завершить ошибкой.
5. Повторить сохранение успешно.

Результат: модель содержит одну запись на 20 байт, а SQLite — записи на 20 и 10 байт. Последующий отчёт завышает трафик.

Рекомендуемое исправление: подтверждать обработку очереди после успешного commit либо при ошибке возвращать в очередь и изменения, и удаления.

Регрессионная проверка: после временной ошибки и успешной повторной записи содержимое SQLite соответствует модели, лишняя запись отсутствует.

**5. Средний приоритет: направление TCP наследуется от прежнего владельца PID**

Места: `model.py:234–235`, `model.py:287–299` (`_apply_stop`, `_is_inbound`).

Причина: `accept_ports` хранит пары `(pid, port)` и не очищает их при завершении или смене экземпляра процесса.

Воспроизведение: old.exe с PID 100 принимает подключение на порт 50000, завершается; new.exe получает PID 100 и отправляет данные с локального порта 50000 на 8.8.8.8:443. Модель создаёт адресат `('TCP', '8.8.8.8', 50000, True)` — то есть входящее соединение и неверный для исходящего соединения порт.

Рекомендуемое исправление: связывать такие сведения с экземпляром процесса и временем жизни соединения; очищать их при завершении/смене владельца PID.

Регрессионная проверка: новый экземпляр не наследует признаки входящих соединений старого.

**6. Средний приоритет: обновление времени активности TCP не сохраняется в SQLite**

Место: `model.py:439–441` (`sync_tcp`).

Причина: чтение TCP-таблицы обновляет `proc.last_seen`, но не помечает запись изменённой. Если других изменений нет, запись пропускается при сохранении.

Воспроизведение: сохранить снимок открытого соединения в момент 100, затем обработать такой же снимок в момент 200. В памяти `last_seen == 200`, в SQLite остаётся 100, `collect_dirty()` возвращает пустые изменения.

Последствие: после перезапуска отчёты и отбор по давности используют устаревшую дату; это также влияет на очистку истории по сроку хранения.

Рекомендуемое исправление: помечать процесс изменённым при изменении сохраняемого `last_seen`. Время последнего обмена самого адресата (`Endpoint.last`) не обязательно обновлять для тихого соединения: у него другая семантика.

Регрессионная проверка: после нового TCP-снимка, сохранения и загрузки время активности процесса актуально.

**7. Средний приоритет: после появления нового интерфейса UDP может отображаться с неверным адресатом**

Места: `etw.py:692–698` (`_on_net`), `model.py:336–340` (`_apply_traffic`), `monitor.py:80`.

Причина: для UDP Receive адреса требуют нормализации направления. Код пытается распознать свой адрес по `local_ips`. Набор заполняется при запуске и дополняется TCP-таблицей. Новый VPN-интерфейс без TCP-соединений может ещё отсутствовать в этом наборе.

Синтетическое воспроизведение через настоящий обработчик `EVENT_RECORD`: после старта добавить VPN с адресом 10.8.0.2, не добавляя TCP на нём; передать событие UDP Receive для ответа DNS 8.8.8.8:53 → 10.8.0.2:55000. Модель показывает удалённый адрес 10.8.0.2 и входящее соединение вместо адресата 8.8.8.8.

Семантика UDP Receive дополнительно сверена с обработчиком SystemInformer: https://github.com/winsiderss/systeminformer/blob/master/plugins/ExtendedTools/etwmon.c . Это синтетическая проверка, а не захват реального трафика VPN в Windows.

Рекомендуемое исправление: нормализовать адреса и порты UDP Receive по виду события, обновлять локальные адреса при изменениях интерфейсов. Сохранить корректность IPv4/IPv6, отправки/приёма и localhost.

Регрессионная проверка: ответы UDP на новом интерфейсе учитываются у реального удалённого узла с правильными портами и направлением.

**8. Средний приоритет: второй экземпляр в другой Windows/RDP-сессии может остановить первый**

Места: `winapi.py:208` (`acquire_single_instance`), `etw.py:510`, `etw.py:537–543` (`EtwSession.start`).

Причина: мьютекс `Local\NetActivityMonitor.SingleInstance` действует внутри пользовательской сессии, а имя ETW `NetActivityMonitor` общее. При `ERROR_ALREADY_EXISTS` приложение без проверки считает существующий сеанс оставшимся после аварии и останавливает его.

Воспроизведение с заглушками Windows API подтвердило последовательность: `StartTrace` → `ERROR_ALREADY_EXISTS` → `ControlTrace(..., STOP)` → повторный `StartTrace`. Результат на двух живых Windows-сессиях отдельно не проверялся.

Рекомендуемое исправление: согласовать область блокировки и область имени ETW либо использовать уникальные имена. Не останавливать существующий сеанс без проверки его владельца и состояния.

**Дополнительные замечания и ограничения**

- `model.py:263–266,429–430`: у завершённого экземпляра после повторного использования PID может остаться ненулевое число открытых соединений. В воспроизведении старая запись сохраняет `conns=1` после пустого TCP-снимка; новый экземпляр имеет 0. Обнулять счётчик при завершении либо пересчитывать все затронутые записи.
- `gui.py:318–344`, `storage.py:72–92`, `console.py:77–105`: фильтры периода отбирают недавно активные процессы, но их счётчики остаются накопленными за всё время. В воспроизведении процесс передал 1 000 000 байт десять дней назад и 10 сейчас; отчёт `--days 7` показывает 1 000 010 байт. Это ограничение семантики: если нужен объём именно за период, необходимо хранить данные по временным интервалам. Если задуман только отбор по последней активности, это надо прямо обозначить в интерфейсе и справке.
- `firewall.py:119,219,286`: проверка служб для svchost пропускает `['Any']` без предупреждения и передаёт это значение в `-Service`; собственный разбор программы считает `Service='Any'` отсутствием ограничения конкретной службой. Подтверждены пропуск проверки и формирование параметра, но эффект нативного `New-NetFirewallRule -Service Any` здесь не проверен. Документация netsh описывает `service=any` как применение ко всем службам: https://learn.microsoft.com/windows-server/administration/windows-commands/netsh-advfirewall . Для устранения потенциального обхода защиты svchost следует отклонять зарезервированные значения и разрешать конкретные короткие имена существующих служб; семантику проверить на Windows.
- `winapi.py:411–423`: теряется IPv6 scope ID. Одинаковые link-local адреса на разных интерфейсах становятся неразличимыми. Это ограничение для нескольких локальных интерфейсов, а не ошибка всех IPv6-подключений.
- `model.py:333–335`: синтетически показано, что старый пакет с timestamp 2.5, обработанный после старта нового владельца PID в момент 10, записывается новому процессу. Реальная возможность такого порядка доставки в конкретной версии Windows не установлена. Рассматривать как кандидат для интеграционного теста, а не как доказанную частую ошибку ETW.

**Порядок исправления и критерии готовности**

1. Сохранность действующих правил при ошибках изменения; достоверное сообщение об удалении и состоянии запрета. Одинаковая логика для GUI и CLI.
2. Привязка подробностей и трафика к экземпляру процесса, а не только к PID; очистка состояния соединений при его смене.
3. Восстановление очереди SQLite после ошибок и сохранение времени активности.
4. UDP на новых интерфейсах, конфликт сеансов ETW, уточнение семантики периодов и валидации служб.
5. Добавить регрессионные тесты на конкретные сценарии выше и повторно выполнить штатные тесты.
6. На Windows 10/11 проверить отдельную тестовую программу: исходящий TCP/UDP по IPv4/IPv6, запрет одного/обоих направлений, снятие и временное отключение запрета, отказы команд, перезапуск монитора, подключение VPN после старта. Сохранность правил после перезагрузки проверить отдельно.

Действие блокировки проверять реальными попытками соединения и чтением правил. Отсутствие роста счётчиков монитора само по себе не доказывает, что Windows Firewall блокирует трафик.

Этот документ фиксирует результаты аудита и рекомендуемые изменения. Исправления исходников не выполнялись; новые проверки на Windows не следует объявлять пройденными до их фактического проведения.
