**V12-1. P2: одинаковое имя exe в разных каталогах может скрыть смену владельца PID**

Места: `model.py:576–594` (`_same_instance`), `model.py:625–630` (`fill_details`).

При проверке пути берётся только basename. Поэтому `C:\Old\app.exe` и `C:\Other\app.exe` считаются совпадающим исполняемым файлом. Если `proc.started` уже известен, допускается расхождение времени создания до `START_MATCH = 0.5` секунды. При этом не применяется более строгая проверка относительно `first_seen`.

Воспроизведение на модели:

1. Из события start создан old-экземпляр PID 100 с путём `C:\Old\app.exe`, время 100.0.
2. В момент 100.1 он передал 10 байт.
3. До обработки событий завершения/нового запуска запрос по PID возвращает сведения другого экземпляра: `C:\Other\app.exe`, время создания 100.4.
4. `fill_details()` принимает эти сведения за старый экземпляр и переписывает его путь и время запуска.

Фактически:

```text
[(path='C:\Other\app.exe', started=100.4, sent=10)]
```

Ожидается сохранение прежней записи `C:\Old\app.exe` с 10 байтами и создание отдельной записи нового процесса. Сейчас трафик приписывается другому пути; этот путь затем может попасть в ручной выбор программы для блокировки. Сама программа автоматически другую программу не блокирует.

Рекомендация: если известны полные пути, сравнивать нормализованные полные пути, а не только имена файлов. При известном времени создания сохранять идентичность экземпляра и не принимать новое время, противоречащее уже подтверждённому наблюдению старого процесса. Погрешность ETW-времени и точное время создания из Windows лучше хранить отдельно; простое уменьшение допуска не решает все варианты.

Критерий исправления: приведённый сценарий оставляет 10 байт у старого exe и не переписывает его путь. Проверить также два экземпляра одного и того же полного пути, появившиеся почти подряд, чтобы исправление не ограничилось сравнением каталогов.

**V12-2. P2 при запоздавшей доставке: допуск SLACK присваивает пакет уже новому процессу, хотя старый подходит точно**

Место: `model.py:300–311` (`_instance_at`), `SLACK = 0.25` в `model.py:26`.

Накопитель уже разделяет пакеты по границам жизни PID. Но поиск владельца перебирает экземпляры от нового к старому и расширяет их время жизни допуском. Поэтому пакет, отправленный до запуска нового процесса, может попасть в его допуск и не дойти до проверки старого экземпляра, внутри которого он действительно был отправлен.

Воспроизведение:

1. old.exe: start=1.0, stop=3.0.
2. new.exe с тем же PID: start=3.1.
3. После обработки start нового процесса поступают события для одинаковых адресов и портов: старый пакет timestamp=2.9 размером 7 байт и новый timestamp=3.2 размером 9 байт.

Ожидается:

```text
old.exe = 7 байт
new.exe = 9 байт
```

Фактически в обоих порядках доставки пакетов:

```text
old.exe = 0 байт
new.exe = 16 байт
```

Старый пакет попадает в допуск нового: `2.9 >= 3.1 - 0.25`. При этом старый экземпляр имеет точный подходящий интервал 1.0–3.0.

Рекомендация: сначала искать совпадение по достоверным границам времени жизни без расширения, затем при необходимости применять отдельную обработку неопределённости. Нельзя отдавать предпочтение допуску нового экземпляра, если существует точное совпадение со старым. Проверить оба порядка доставки и границы рядом со start/stop.

Это синтетическое воспроизведение остаточного дефекта поддержки запоздавших событий. Оно не доказывает, что такие события часто приходят в реальной Windows, и не означает, что весь учёт трафика работает неверно.

**Репозиторий и доступ**

На момент проверки GitHub сообщил `visibility=private` для LabCodex; подключение сохранило доступ на чтение и запись. Это позволило получить архив из приватного репозитория.

`Netmon` создан как ветка, а не папка. Ветка хранит отдельную версию всего содержимого репозитория, поэтому остальные файлы остаются видны. Архив 1.2 на момент проверки есть в ветке Netmon и отсутствует в main. Это нормальная работа GitHub; новые файлы ветки не появляются в main автоматически.

Чтобы создать именно каталог в выбранной ветке, можно выбрать `Add file → Create new file` и указать имя вроде `netmon/README.md`, затем сохранить. GitHub создаст каталог `netmon` вместе с файлом. Пустые папки Git не хранит. Перемещение архивов, слияние веток и настройки доступа при этой проверке не изменялись.

Дальнейшая проверка: закрыть два случая выбора экземпляра процесса, затем проверить на Windows реальный TCP/UDP по IPv4/IPv6, блокировку/снятие/временное отключение запрета, сохранение правил после перезагрузки и подключение VPN после старта. По доступным тестам версия 1.2 существенно лучше 1.1; утверждать отсутствие всех багов или полную проверенность Windows-компонентов пока нельзя.
